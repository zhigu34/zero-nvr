# Multiplexed Live Grid Preview Design

**Date:** 2026-09-27

## Context

The live grid supports 1, 4, 9, and 16 tiles. A low-quality H.265 tile
currently opens its own endless multipart JPEG response. The production
service is exposed directly by Uvicorn over HTTP/1.1, so these long-lived
responses compete for the browser's small per-origin HTTP/1.1 connection
pool. In a nine-tile grid, five JPEG streams commonly occupy the available
connections while the remaining tiles stay at "connecting".

This is a transport ceiling rather than a five-camera product limit. The
camera-recorder reference avoids it by carrying all grid JPEG frames over
one WebSocket.

## Goals

- Allow 9- and 16-tile grids to receive all H.265 JPEG previews through one
  browser connection.
- Preserve direct H.264 WebRTC/HLS playback and focused H.265 compatibility
  playback.
- Keep preview CPU, bandwidth, and memory bounded for each grid size.
- Isolate a failed camera so it cannot interrupt other grid tiles.
- Reuse the existing authenticated MediaSession as the authority for every
  subscribed camera source.
- Close FFmpeg processes promptly when a tile unsubscribes, a MediaSession
  expires, the socket disconnects, or the page becomes hidden.

## Non-goals

- This change does not add native H.265 browser playback.
- It does not combine camera decoding into one FFmpeg process.
- It does not change recording, detection, audio, focused playback, or the
  bounded H.264 compatibility-transcode capacity.
- It does not require TLS or HTTP/2 and does not add domain sharding.

## Selected Architecture

The live page owns one `LivePreviewWall` client for all visible low-quality
H.265 tiles. Each tile still resolves its own live descriptor and receives a
MediaSession ID. Instead of opening `/preview.mjpeg`, the tile registers its
slot, camera ID, and MediaSession ID with the page-level client. The client
synchronizes the complete desired subscription set over one same-origin
WebSocket.

The backend validates every requested camera and MediaSession, starts one
bounded FFmpeg JPEG producer per accepted H.265 tile, and multiplexes the
latest complete JPEG frame from each producer onto the WebSocket. Directly
playable H.264 tiles never register with this channel.

The existing multipart JPEG endpoint remains available for a focused/high
quality startup bridge and diagnostics, where only one tile uses it. Grid
playback does not silently fall back to one multipart response per tile,
because that would reintroduce the HTTP/1.1 ceiling.

## Wire Protocol

The endpoint is `WS /api/v1/live/previews/ws`.

The client sends a complete synchronization message whenever the layout,
visible cameras, playback state, or a tile's MediaSession changes:

```json
{
  "type": "sync",
  "version": 1,
  "layout_slots": 9,
  "streams": [
    {
      "slot": 0,
      "subscription_id": 42,
      "camera_id": "00000000-0000-0000-0000-000000000001",
      "media_session_id": "00000000-0000-0000-0000-000000000002"
    }
  ]
}
```

`layout_slots` is limited to `4`, `9`, or `16`; focused and one-tile views
use the existing full-motion path. Slots must be unique integers from zero
through `layout_slots - 1`, and a message may contain at most 16 streams.
`subscription_id` is an unsigned 32-bit value generated by the client and
changes whenever a slot registers a different camera or MediaSession.
The server diffs the message against the active subscriptions: unchanged
producers continue running, removed or changed producers stop, and new ones
start.

Server text messages use JSON:

- `{"type":"synced","version":1}` confirms that the synchronization
  message was accepted.
- `{"type":"ready","slot":0,"subscription_id":42}` reports that a slot
  produced its first complete JPEG frame.
- An `error` message carries `slot`, `subscription_id`, `code`, and `message`
  fields and reports a per-slot failure without closing the socket.
- `{"type":"fatal","code":"...","message":"..."}` reports a socket-wide
  protocol or authentication failure before closure.

Every binary message contains one protocol-version byte, one slot byte, a
four-byte big-endian subscription ID, and one complete JPEG image:

```text
[0x01][slot 0..15][subscription_id uint32][JPEG beginning FF D8 ... FF D9]
```

The frontend accepts a ready, error, or JPEG message only when both its slot
and subscription ID match the current registration. This prevents an already
queued frame from a removed camera appearing in a newly assigned tile.

Sync text messages are limited to 64 KiB. Unknown versions, malformed JSON,
duplicate slots, invalid UUIDs, oversized messages, and out-of-range layouts
produce a `fatal` response and immediately close the socket with status 1008.
A valid sync whose individual subscription cannot be authorized or started
produces an `error` for only that slot.

## Preview Profiles and Backpressure

The server derives preview limits from `layout_slots`; clients cannot request
arbitrary dimensions or frame rates:

| Layout | Maximum width | Frame rate |
| --- | ---: | ---: |
| 4 tiles | 640 px | 5 FPS |
| 9 tiles | 480 px | 3 FPS |
| 16 tiles | 320 px | 2 FPS |

Each slot has at most one pending JPEG frame. A newly produced frame replaces
an older unsent frame for the same slot. The sender visits ready slots fairly,
so a slow browser drops stale frames instead of accumulating latency or
unbounded memory. A JPEG payload is limited to 2 MiB; an oversized producer
frame is reported as a slot error and that producer is stopped.

## Backend Components

`backend/app/modules/cameras/live_preview.py` changes from emitting opaque
multipart chunks to yielding complete JPEG frames. FFmpeg uses `image2pipe`,
and a small incremental parser extracts images between JPEG SOI and EOI
markers. The existing multipart HTTP endpoint wraps these complete frames in
multipart boundaries, so its public behavior remains compatible.

A new `backend/app/modules/cameras/live_preview_wall.py` owns:

- protocol parsing and validation;
- the active slot-to-preview-session map;
- diffing synchronization messages;
- one-latest-frame-per-slot buffering;
- fair binary-frame delivery;
- producer and socket cleanup.

A new router module exposes the WebSocket and is included before the dynamic
camera routes under `/api/v1`. It uses the existing database, camera scope,
MediaSession registry, and ZLMediaKit internal RTSP source resolution rather
than accepting a caller-supplied media URL.

## Authentication and Authorization

The same-origin browser session cookie is sent with the WebSocket handshake.
The endpoint requires an active interactive session with `camera.view`.
Because WebSocket handshakes are not protected by ordinary browser CORS, the
server also requires the `Origin` scheme/host/port to match the request host.

Every synchronized stream is authorized independently:

- the camera must be visible in the user's effective camera scope;
- the MediaSession must belong to that user and camera;
- the session's stored profile and purpose determine the ZLM source;
- camera credentials and raw RTSP URLs never cross the socket.

Authorization is checked on every new or changed subscription. MediaSession
revocation registers a cleanup callback that stops the matching producer and
emits a slot error when the socket remains open.

## Frontend Components

A new `frontend/src/live/previewWall.ts` module owns the single WebSocket,
subscription map, reconnect backoff, protocol decoding, and frame dispatch.
`LiveView.vue` creates one controller, supplies the current layout size, and
passes an explicit controller plus stable slot index to each tile.

For a low-quality H.265 descriptor, `LiveCameraTile.vue` registers with that
controller and waits for the first frame before marking the tile active. The
tile converts each JPEG to an object URL, replaces and revokes the preceding
URL, and unregisters on source/quality changes, suspension, playback stop, or
unmount. For focused/high-quality playback it leaves the shared channel and
uses the existing compatibility path, retaining the existing single-stream
JPEG bridge while full video starts.

When the shared socket disconnects, the last valid frame may remain visible
with a reconnecting state. The controller reconnects after 1, 2, 4, 8, and at
most 15 seconds, then resynchronizes current subscriptions. A per-slot backend
error shows the existing retry UI for that tile and leaves other tiles active.

## Lifecycle and Failure Isolation

- A page owns exactly one preview WebSocket.
- A slot owns at most one FFmpeg preview process.
- Synchronizing an unchanged slot does not restart its process.
- Removing a slot waits for process cleanup before its registration is
  forgotten.
- Socket disconnect cancels every producer and unregisters every MediaSession
  cleanup callback.
- MediaSession expiry stops only its associated slot.
- One FFmpeg exit, malformed camera stream, or offline camera produces a
  per-slot error and does not close the shared socket.
- Page visibility suspension closes the socket and therefore all grid preview
  producers; visibility resume creates a new socket and fresh MediaSessions.

## Alternatives Considered

### TLS plus HTTP/2

HTTP/2 can multiplex responses, but the current appliance is intentionally
usable over direct plain HTTP and Uvicorn does not provide browser-compatible
cleartext HTTP/2 for this deployment. Requiring a TLS reverse proxy would make
correct multi-camera behavior depend on external deployment configuration.

### Multiple hosts or ports

Spreading MJPEG requests across origins would work around browser limits but
duplicates routing, cookies, CORS, and certificate configuration. It also
keeps one long-lived HTTP request per camera.

### One multipart response containing every camera

This could use one HTTP connection, but browsers cannot bind different parts
of one multipart image response to separate `<img>` elements. It would need a
custom parser and framing protocol anyway, while WebSocket already supplies
message framing and bidirectional subscription updates.

## Testing

Backend tests cover:

- JPEG parsing across split, multiple, noisy, and oversized chunks;
- profile derivation for 4, 9, and 16 tiles;
- sync validation and incremental diff behavior;
- same-origin session authentication and camera-scope enforcement;
- cross-user and cross-camera MediaSession rejection;
- complete binary framing and fair latest-frame delivery;
- per-slot FFmpeg failure isolation;
- MediaSession revocation and socket-disconnect cleanup;
- compatibility of the existing multipart endpoint.

Frontend tests cover:

- one WebSocket for 9 or 16 H.265 grid tiles;
- subscription synchronization as descriptors arrive and tiles change;
- binary-frame routing to the correct tile;
- stale-frame rejection after a slot is reassigned;
- object URL replacement and revocation;
- reconnect and resynchronization without duplicate sockets;
- one tile error without disturbing other frames;
- no shared preview subscription for direct H.264 or focused playback;
- layout-specific resource profiles reflected in sync messages.

## Acceptance Criteria

1. A nine-camera H.265 grid issues one preview WebSocket rather than nine
   endless MJPEG HTTP requests.
2. All nine slots can receive frames over a plain HTTP deployment without the
   five-stream stall.
3. A sixteen-tile grid enforces 320 px at 2 FPS and keeps at most one pending
   frame per slot.
4. Direct H.264 tiles retain their current startup path and latency.
5. Focusing an H.265 tile upgrades it to the existing full-motion compatibility
   stream and removes it from the shared grid preview.
6. Disconnecting the page or expiring one MediaSession leaves no orphaned
   preview FFmpeg process.
7. All backend, frontend, and deployment CI checks pass before merge.
